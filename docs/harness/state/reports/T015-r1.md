## 五、缺陷清单（按严重度）

### [MAJOR] D1 · E7/E8 假绿：制品 sha256 / 版本断言从未被执行
- 位置：`tests/upgrade/test_upgrade_flow.sh:759-777`（E7）、`:779-802`（E8）
- 复现：按 E7 的 `-e` 参数在最小沙箱跑 `playbooks/upgrade.yml --limit cp1`：
  `upgrade_bin_dir` 指向空的 `$SB/var/fake-bin`，`backup.yml:78-89` 复制旧二进制失败 →
  `Source .../var/fake-bin/kube-apiserver not found`，play 在 `backup` 阶段中止。
  证据：`/tmp/opencode/t015-e7probe/e7.log:86-87`（失败点）、`e7.log:22/33`（
  `grep -qiE 'sha256|checksum|校验'` 命中的是任务名「交叉校验」与「未校验」）。
  E8 同理：`e8.log` 也在 `backup` 中止，`grep -qiE '版本|version'` 命中「目标版本」等无关文本。
- 期望：E7 命中制品 checksum 失败、E8 命中「制品版本不符」。
- 实际：两条断言从未执行；把假 bin 目录填入旧二进制后，同一参数才真实触发：
  `e7b.log:146`（`checksum ... did not match`）、`e8b.log:166`（`制品版本不符：期望 v1.32.13`）。
- 影响：role 行为本身正确（已由 e7b/e8b 证明），但套件对「sha256 校验」「制品版本校验」
  两条契约验收项没有证据；后续回归（如删除 `component.yml:32-75`）不会被这套测试发现。
- 建议方向：E7/E8 不要覆盖 `upgrade_bin_dir`（或先放入 1.31 旧二进制），只覆盖
  `upgrade_artifact_dir`/`upgrade_download_url_base`；断言改为匹配 `did not match` /
  `制品版本不符`，并断言 `upgrade:binaries | 断言` 任务确实出现（或日志含 `checksum` 而非 `校验`）。

### [MINOR] D2 · 回滚日志断言可被「skipped」任务名命中
- 位置：`tests/upgrade/test_upgrade_flow.sh:1038-1041`
- 复现：牙齿 T3（跳过 etcd restore）时，`回滚日志含 etcd 快照恢复` 与 `回滚日志含数据目录换入`
  仍 PASS（Ansible 打印 `skipping: [cp1]` 时也带任务名）；只有 ConfigMap 断言变红。
- 期望：断言证明 restore/换入真实执行。
- 建议：改为断言 `changed: [cp1]` 或 `snapshot restore` 的输出行，且不匹配 `skipping:` 行。

### [MINOR] D3 · 两处恒真/弱断言
- `:1122` `kubepods 清理仅停本次新建 slice 且无失败`：没有新建 slice 时恒为真；
- `:352` `sandbox 资产不写宿主 /etc/systemd/system`：字符串根本不存在时恒为真。
- 建议：前者断言「本次确有新增 slice 被停」或删除；后者改为解析 sandbox_root 前缀。

### [MINOR] D4 · E8 的前置断言是恒真式
- 位置：`:787-788`「假制品 sha256 与注入的 upgrade_known_sha256 一致」——两者由同一文件现算，
  恒相等。建议断言「该 sha ≠ 官方 sha」以证明「sha 对但版本错」的语义。

### [MINOR] D5 · 目标版本重跑仍可能裁剪备份（`upgrade_needed=false` 时）
- 位置：`roles/upgrade/tasks/validate.yml:140-151`（裁剪任务没有 `upgrade_needed` 条件）
- 复现：最小沙箱（二进制已是 1.32.13、备份 2 个、`upgrade_backup_retention=1`）跑
  `--tags upgrade:validate` → `changed=1`，目录数 2→1（`/tmp/opencode/t015-e7probe2/v.log`）。
- 影响：契约 C1「同命令连跑两次 changed=0」在主场景成立（第二次时目录数已 ≤ 保留数），
  但「目标版本无操作重跑」仍可能删除旧备份，属未声明的副作用。建议加 `upgrade_needed` 条件。

### [MINOR] D6 · 任务名在 loop 外引用 `item` 产生模板告警
- 位置：`roles/upgrade/tasks/backup.yml:67`、`:78`（任务名含 `{{ item | basename }}`）
- 证据：`/tmp/opencode/t015-e7probe/e7.log:86` 任务名显示 `<< error 1 - 'item' is undefined >>`。
  功能不受影响（仅日志噪音），建议任务名改用不含 `item` 的固定文案。

### [MINOR] D7 · 回滚默认成员名/peer URL 与本项目 etcd role 默认不一致
- 位置：`roles/upgrade/defaults/main.yml:131-134`（`member_name: default`、
  `initial_peer_url: http://localhost:2380`）vs `roles/etcd/defaults/main.yml:40`
  （`etcd_member_name: "{{ inventory_hostname }}"`）+ TLS peer。
- 复现：用 `--name=default` restore 后以 `--name=etcd1` 启动单成员 etcd：可启动、数据可读
  （本机探针），但 member 的 PEER ADDRS 被固定为 `http://localhost:2380`；3 成员场景需显式覆盖。
- 影响：单成员/沙箱不阻塞；契约 §5 的回滚命令未展示这些必需覆盖项（多成员已声明未验证）。
  建议 README/§5 明示 `-e upgrade_rollback_etcd_member_name=<inventory_hostname>`
  与 `-e upgrade_rollback_etcd_initial_peer_url=<真实 peer URL>`。

### [INFO] D8 · 回滚后 PKI/kubeconfig 哈希比对不具区分度
- `test_upgrade_flow.sh:1084-1086`：升级过程本就不改 PKI/kubeconfig，回滚后相等是必然；
  真正的判别证据是二进制哈希、`/version`、ConfigMap 消失。报告/契约 D5 不应把这部分当作主证据。
