## 5. 非阻塞改进项（PASS 仍需列出）

### [MINOR-1] D3 的“role 层第二道防线”不成立：无 `serial: 1` 时 3 个成员会先全部重启，再执行 quorum 闸门
- 位置：
  - `roles/etcd/tasks/rolling_restart.yml:14-36`：`throttle: 1` 只作用于“重启任务”本身，
    `include_tasks: wait_member_healthy.yml` 是**后续任务**，不受同一 throttle 锁保护。
  - `roles/etcd/tasks/wait_member_healthy.yml:46-54`：assert 发生在所有主机重启任务均已执行之后。
  - `roles/etcd/README.md:131-134`、`docs/harness/state/contracts/T005.md:98-104`：
    声称“每次重启后等待……任一失败立即中止，不会继续重启下一个成员”“第二道防线”。
  - `tests/etcd/sandbox.yml:37`：公开测试用 `serial: 1` 掩盖了该语义。
- 复现（已执行，主工作区未动）：
  ```bash
  # 独立 3 主机 inventory（同机不同端口），不设 serial，默认 forks
  # /tmp/opencode/t005r2_indep/{inv.ini,restart_multi.yml}，改 etcd_heartbeat_interval 触发 handler
  grep -n 'RUNNING HANDLER \[etcd : etcd:restart | 逐个重启' -A6 /tmp/opencode/t005r2_indep/multi.log
  # 295: changed: [indep1] changed: [indep2] changed: [indep3]（三个成员先全部重启）
  # 303: 才出现“等待 indep1 endpoint 恢复 healthy”
  # 84:  samples=107 min_healthy=1；handler rc=0
  ```
- 期望：在未设置 play 层 `serial: 1` 时，role 也应在“重启成员 N → 等其 health + quorum → 再重启 N+1”的
  同一临界区内完成（例如把单成员 restart+wait 封装进一个任务文件，并用 `include_tasks` + `throttle: 1`），
  或把“必须 `serial: 1`”写成硬前提并在 assert 中检测（`ansible_play_batch|length`）。
- 实际：`throttle: 1` 只保证同一时刻执行一个 restart 命令，不保证等待完成前不重启下一个；
  生产 play 若忘记 `serial: 1`，3 个成员会在数秒内先后全部重启，出现 107 次采样中最低仅 1 个 healthy 端点
  （端点健康数短暂低于多数派，存在写不可用风险），而 handler 仍成功退出。
- 影响：T005 的 A25 在测试配置下 PASS；但 README/契约的“第二道防线”表述与真实语义不符，
  且 T006/T007 若不在 etcd 重启的 play 上设置 `serial: 1`，会复现该风险。
- 建议方向：优先实现“restart+wait 同一 throttle 临界区”；否则把 README/契约改成“role 不提供跨主机
  第二道防线，必须 `serial: 1`”，并在 T006/T007 的 play 中显式设置 + 增加断言。

### [MINOR-2] D3 测试与 `serial: 1` 强耦合，且“重启次数/等待成员”断言依赖日志文本
- 位置：`tests/etcd/test_etcd_role.sh:617-625`、`tests/etcd/sandbox.yml:37`。
- 复现：独立 worktree（T3b）仅删除 `tests/etcd/sandbox.yml:37` 的 `serial: 1`，以 `ANSIBLE_FORKS=1` 跑全套：
  实测 `PASS=221 FAIL=4`、rc=1；FAIL 为 `D3 三个成员逐个重启（3 次重启钩子执行）`、
  `D3 etcd2/etcd3 重启后等待...`、`D3 每个成员...校验（3 次）`。这些是日志文本计数，不是真实 quorum 失败。
- 另一实验（T3c：保留 `serial: 1`，让第一台主机在 handler 内重启全部 3 成员）：
  实测 `PASS=224 FAIL=1`，只有“3 次重启钩子执行”FAIL，quorum 采样仍 PASS（3 次 hook 仍逐个完成）。
  说明该采样对“短窗口内的连续重启”不敏感。（两个独立 worktree 已按收尾要求移除，未留日志文件。）
- 建议方向：D3 断言改为基于 `/proc` 进程存活数或 etcd member 状态（而非日志行数），
  并增加一个“无 serial 也必须保 quorum”的负例；若保留日志断言，需用 `grep -c` 固定单次运行日志文件。

### [NIT-1] 采样口径：0.25s `endpoint health` 会把 leader 选举瞬时值误判为丢 quorum
- 位置：`tests/etcd/test_etcd_role.sh:447-451`、`:625`；独立复现 `run2.log:71-72`。
- 现象：逐个重启（leader 重启）时 7 次采样 min=1，但 3 个成员进程均存活、数据可读写、逐成员闸门 PASS。
- 建议：采样“进程存活数/`member list` 中在线成员数”，或允许 <2 的瞬时值在 2s 内恢复；避免 CI 偶发 FAIL。

### [NIT-2] `certs.yml` 只断言私钥 uid/mode，未断言 gid
- 位置：`roles/etcd/tasks/certs.yml:79-89`（`item.stat.uid == 0`、`mode == etcd_cert_key_mode`，无 `item.stat.gid`）。
- 测试侧已断言 group（`test_etcd_role.sh:389-399`），但 role 内自检漏 gid；若分发任务误用其它组，
  role 不会 fail-fast。建议增加 `item.stat.gid == etcd_cert_group 的 gid`（或 `gr_name`）。
