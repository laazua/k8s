## 4. 缺陷清单（按严重度）

### [MAJOR] M4 · T007 套件非密闭：kubectl 绕过本地缓存每次重下，CDN 限速时全量门禁必红

- 位置：
  - `tests/control-plane/sandbox_stack.yml:21`：`dest: "{{ sandbox_root }}/usr/local/bin/kubectl"`（显式 dest）；
  - `tests/control-plane/test_control_plane_roles.sh:352-354`：把 4 个制品复制到 `$SB/opt/k8s/artifacts`（缓存），但 kubectl 的下载项不使用它；
  - `roles/download/tasks/main.yml:46`：`'dest': item.dest | default(download_cache_dir ~ '/' ~ _name)` → 显式 dest 优先；
  - `roles/download/tasks/main.yml:66-84`：`get_url` 在 dest 不存在时**必须发网络请求**（120 s timeout × 3 重试）。
- 复现：
  ```bash
  cd /tmp/opencode/eval-t007
  env -u PYTHONPATH -u ANSIBLE_PLAYBOOK make test   # run2
  # → T007: stack playbook 失败；/tmp/opencode/t007_stack.log 停在
  #   TASK [download : download:fetch | 下载并强校验制品]
  # → == 汇总: PASS=169 FAIL=100 ==；rc=2
  curl -r 0-1048575 -o /dev/null -w '%{speed_download}\n' \
    https://dl.k8s.io/v1.31.0/bin/linux/amd64/kubectl   # 本次实测 ~39–55 KB/s
  ```
- 期望：套件自带的 4 个制品缓存被真正使用（`kubectl` 从 `$CACHE`/`$SB/opt/k8s/artifacts` 安装），全量门禁**不依赖外网吞吐**，两次连跑均 exit 0。
- 实际：每个 T007 首跑都把 56 MB kubectl 从 `dl.k8s.io` 重新下载；本次评估期间 CDN 吞吐降到 ~40–55 KB/s，56 MB 需 ~17 min，远超 `get_url` 120 s 与套件 600 s 上限 → run2 与后续 T007 重跑均在同一 fetch 卡死（169/100）。run1（12:35 左右）网络快时曾绿，因此这是**确定性的缓存接线缺陷 + 外部网络劣化**，不是随机测试逻辑错误。
- 影响：A22「全量门禁 ×2」不可在弱网/离线环境复现；评估门禁红。产品 role 本身不受影响（run1 已证）。
- 建议方向（二选一，改测试不改产品）：
  1. `tests/control-plane/sandbox_stack.yml`：把 kubectl 的 `dest` 改为 `{{ sandbox_root }}/opt/k8s/artifacts/kubectl`（命中缓存），再追加一个 `ansible.builtin.copy` 任务把它安装到 `{{ sandbox_root }}/usr/local/bin/kubectl`（mode 0755）；或
  2. `tests/control-plane/test_control_plane_roles.sh`：在 stack playbook 之前预置 `$SB/usr/local/bin/kubectl`（`cp "$CACHE/kubectl" ... && chmod 0755`），`get_url` 校验命中后即跳过、不发请求。
  修完后在**干净 `git archive` 检出**中 `make test` ×2，要求两次 `27/39/59/100/225/186/269`、`FAIL=0`、exit 0。
