## 4. 缺陷清单（按严重度排序）

### [BLOCKER] B1：生产 unit `User=etcd` 无法读取 T004 默认生成的 root:root 0600 私钥，真实 systemd 启动必失败
- 位置：
  - `roles/etcd/templates/etcd.service.j2:9`（`User={{ etcd_user }}`，默认 `etcd`）
  - `roles/etcd/defaults/main.yml:67-72`（`etcd_user=etcd`）
  - `roles/pki/defaults/main.yml:29`（`pki_key_mode: 0600`）、`:32-33`（owner/group 默认 `root`）
  - `roles/pki/tasks/cert.yml:59-64`（私钥强制 0600 + root:root）
  - `roles/etcd/tasks/validate.yml:83-101`（只 `stat.exists`，未校验属主/可读性）
  - 测试侧掩盖：`tests/etcd/sandbox.yml:18-20`（`pki_file_owner: omit`）、`:32-35`（`etcd_file_owner: omit`、`etcd_manage_user: false`），`tests/etcd/test_etcd_role.sh:270` 只断言 `User=etcd` 文本
- 复现（独立，非仓库测试）：
  ```bash
  SB=$(mktemp -d /tmp/opencode/t005pkiowner.XXXXXX)
  # 以 become: true 跑 pki role（使用生产默认 owner，不覆盖 pki_file_owner）
  ansible-playbook -i tests/etcd/inventory.ini /tmp/opencode/t005_r1_indep/pki_probe.yml \
    -e "{\"sandbox_root\":\"$SB\"}"
  sudo stat -c '%U:%G %a %n' "$SB/etc/kubernetes/pki/etcd/server.key"
  # → root:root 600 .../server.key（目录 root:root 700）
  sudo -u nobody cat "$SB/etc/kubernetes/pki/etcd/server.key" >/dev/null
  # → PERMISSION_DENIED
  # 直接以非 root 用户按 unit 的 TLS 参数启动 etcd（从官方 tarball 取二进制）：
  tar -xzf /tmp/opencode/etcd-cache/etcd-v3.5.16-linux-amd64.tar.gz -C /tmp
  cp /tmp/etcd-v3.5.16-linux-amd64/etcd /tmp/etcd-nobody && chmod 755 /tmp/etcd-nobody
  sudo -u nobody /tmp/etcd-nobody --name=nobodyprobe \
    --data-dir=/tmp/etcd-nobody-data \
    --listen-client-urls=https://127.0.0.1:19999 --advertise-client-urls=https://127.0.0.1:19999 \
    --listen-peer-urls=https://127.0.0.1:19998 --initial-advertise-peer-urls=https://127.0.0.1:19998 \
    --initial-cluster=nobodyprobe=https://127.0.0.1:19998 \
    --cert-file="$SB/etc/kubernetes/pki/etcd/server.crt" \
    --key-file="$SB/etc/kubernetes/pki/etcd/server.key" \
    --trusted-ca-file="$SB/etc/kubernetes/pki/etcd/ca.crt" \
    --peer-cert-file="$SB/etc/kubernetes/pki/etcd/peer.crt" \
    --peer-key-file="$SB/etc/kubernetes/pki/etcd/peer.key" \
    --peer-trusted-ca-file="$SB/etc/kubernetes/pki/etcd/ca.crt"
  # → exit 1，error: open .../peer.crt: permission denied
  ```
- 期望：`User=etcd` 的服务进程能读取 server/peer 私钥与 CA（例如 etcd role 将 etcd 三对证书/私钥以 `etcd:etcd 0600` 复制/授权，或 pki 以 `root:etcd 0640` 生成并让 unit `SupplementaryGroups=etcd`）；测试至少以非 root 服务用户验证可读性。
- 实际：pki 默认 root:root 0600、目录 0700；etcd 进程（非 root）读取即 `permission denied`，真实 `systemctl start etcd` 会失败。沙箱测试因为 `pki_file_owner: omit` 且 etcd 进程与 pki 文件同属当前用户，完全绕过了这个失败。
- 建议方向：给 etcd role 增加独立的证书属主/组/权限变量（或在 role 内对 etcd server/peer key 做 `copy`/`file` 授权），并在测试中用非 root 用户（或 `setpriv`/`runuser`）启动至少一个成员，断言 key 可读且能通过 TLS 握手。

### [BLOCKER] B2：role 把 `/etc/systemd/system`、`/usr/local/bin` 与 unit 文件 chown 给服务用户，构成提权面
- 位置：
  - `roles/etcd/defaults/main.yml:31`（`etcd_bin_dir` 默认 `/usr/local/bin`）、`:57`（`etcd_unit_dir` 默认 `/etc/systemd/system`）、`:60`（unit mode 0644）、`:67-72`（`etcd_file_owner=etcd`）
  - `roles/etcd/tasks/binary.yml:11-25`（对 `etcd_bin_dir` 等目录 `owner: etcd_file_owner`）
  - `roles/etcd/tasks/config.yml:18-25`（对 `etcd_unit_dir` 设 owner）、`:27-34`（unit 文件 owner 也为 `etcd_file_owner`、mode 0644）
  - 测试侧掩盖：`tests/etcd/sandbox.yml:32-35`（`etcd_file_owner: omit`）
- 复现（独立，非仓库测试；模拟生产默认 owner）：
  ```bash
  SB=$(mktemp -d /tmp/opencode/t005owner.XXXXXX)
  mkdir -p "$SB/etc/systemd/system" "$SB/usr/local/bin" "$SB/opt/k8s"
  sudo chown root:root "$SB/etc/systemd/system" "$SB/usr/local/bin" "$SB/opt/k8s"
  # owner_probe.yml：见 /tmp/opencode/t005_r1_indep/owner_probe.yml
  #   hosts: etcd、become: true、etcd_file_owner: zhangsan（代表默认 etcd）、TLS off、
  #   etcd_instance_layout: co-located、etcd_manage_user/service: false
  ansible-playbook -i /tmp/opencode/t005_r1_indep/inv_tlsoff.ini \
    /tmp/opencode/t005_r1_indep/owner_probe.yml -e "{\"sandbox_root\":\"$SB\"}"
  stat -c '%U:%G %a %n' "$SB/etc/systemd/system" "$SB/usr/local/bin" \
    "$SB/etc/systemd/system/etcd-to1.service"
  # → zhangsan:zhangsan 755 .../etc/systemd/system
  # → zhangsan:zhangsan 755 .../usr/local/bin
  # → zhangsan:zhangsan 644 .../etcd-to1.service
  ```
  在生产默认下即 `etcd:etcd`；且 unit 文件 0644 由 etcd 拥有，etcd 进程可改写自己的 `ExecStart`（指向同样由 etcd 拥有的 `/usr/local/bin/etcd`）。
- 期望：`/etc/systemd/system`、`/usr/local/bin` 与 unit 文件保持 `root:root`；unit 0644 root 所有；二进制 0755 root 所有；仅数据目录 `etcd:etcd 0700`。服务用户不应拥有任何 root 执行路径。
- 实际：role 用同一个 `etcd_file_owner`（默认 etcd）配置数据目录、安装目录、unit 目录和 unit 文件，导致服务用户拥有 systemd 单元目录/文件和 `/usr/local/bin`，可从 etcd 进程提权到 root（写 unit/替换二进制）。
- 建议方向：拆分 `etcd_data_owner/group`（etcd）与 `etcd_root_owner/group`（root）；unit 目录/文件、二进制与 artifact 目录用 root；只有 data-dir 用 etcd。测试用 root 运行 role 后断言 `stat` 的属主，而不是用 `omit` 绕过。

### [MAJOR] D3：生产配置变更会同时重启所有 etcd 成员（缺滚动重启/编排保护）
- 位置：`roles/etcd/handlers/main.yml:8-13`、`roles/etcd/tasks/config.yml:27-34`（unit notify）、`roles/etcd/tasks/service.yml:8-14`（systemd 模块）
- 复现：3 台 etcd 主机按默认 `forks` 跑 role，修改 `etcd_heartbeat_interval`；所有收到 notify 的主机在 play 结束时一起执行 `systemd restart etcd`。
- 期望：至少串行/逐成员重启（或由 T006/T007 用 `serial` 编排），避免 3/3 同时重启导致 quorum 丢失和短时不可用。
- 实际：role 本身没有 `serial`/滚动保护；测试只验证 `changed` 与 handler 被通知（且 `etcd_manage_service=false` 被 skip），无法暴露该风险。
- 建议方向：在 role README/契约中声明由编排层保证滚动；或在 T006/T007 的 play 上设置 `serial: 1` / `max_fail_percentage`，并补一个 `--check`/测试断言。

### [MINOR] D4：A15 的“PID 未变”断言比较的是 shell 变量，不是操作系统进程
- 位置：`tests/etcd/test_etcd_role.sh:397-406`
- 复现：`PIDS_BEFORE`/`PIDS_AFTER` 都取自脚本自己的 `${PID[$n]}`；role 重跑不会修改这些 shell 变量，因此该断言在“role 真的重启了进程”时也可能 PASS。
- 期望：从 `/proc/<pid>/stat` 的 starttime、`ps -o lstart` 或 systemd `MainPID` 读取真实进程身份。
- 实际：壳变量恒等；本轮我用 `/proc/<pid>/stat` 的 starttime 独立验证通过，但测试本身不能捕获该回归。
- 建议方向：在启动成员时记录 `starttime`，重跑后比较；或断言 `systemctl show -p MainPID`（受限环境下用 `/proc`）。
