## 4. 缺陷清单（FAIL）

### [BLOCKER] B1：systemd 读取发行版默认配置，role 渲染到 `/etc/kubernetes/*`，生产服务不会加载 role 配置

- 位置：
  - `roles/haproxy/defaults/main.yml:43-44`：`haproxy_config_dir = .../etc/kubernetes/haproxy`，`haproxy_config_file = .../haproxy.cfg`
  - `roles/haproxy/tasks/config.yml:14-19`：只渲染到上述路径
  - `roles/haproxy/tasks/service.yml:7-12`：`systemd: name=haproxy state=started`
  - `roles/keepalived/defaults/main.yml:55-56`：`keepalived_config_dir = .../etc/kubernetes/keepalived`
  - `roles/keepalived/tasks/keepalived.yml:38-43`：只渲染到上述路径
  - `roles/keepalived/tasks/service.yml:6-11`：`systemd: name=keepalived state=started`
- 复现（非破坏性）：
  ```bash
  grep -nE 'config_(dir|file)' roles/{haproxy,keepalived}/defaults/main.yml
  grep -nE 'systemd:|name:.*(haproxy|keepalived)' roles/{haproxy,keepalived}/tasks/service.yml
  grep -E 'CONFIG=|ExecStart=' \
    /tmp/opencode/t006root/usr/lib/systemd/system/{haproxy,keepalived}.service
  ```
  实测 unit：
  - haproxy：`Environment="CONFIG=/etc/haproxy/haproxy.cfg"`，
    `ExecStart=/usr/sbin/haproxy -Ws -f $CONFIG -f $CFGDIR ...`
  - keepalived：`ExecStart=/usr/sbin/keepalived --dont-fork $KEEPALIVED_OPTIONS`，
    默认读 `/etc/keepalived/keepalived.conf`
  - RPM 包确实会落这两个样例：
    `rpm -qlp /tmp/opencode/rpms/haproxy-*.rpm | grep /etc/haproxy/haproxy.cfg`、
    `rpm -qlp /tmp/opencode/rpms/keepalived-*.rpm | grep /etc/keepalived/keepalived.conf`
- 期望：`haproxy_manage_service=true` / `keepalived_manage_service=true` 时，服务加载 role 渲染的
  `/etc/kubernetes/{haproxy/haproxy.cfg,keepalived/keepalived.conf}`，或 role 渲染到 unit 实际读取的默认路径。
- 实际：服务仍读发行版默认路径。
  - haproxy：没有 `/etc/haproxy/haproxy.cfg` 时 unit `ExecStartPre` 失败；安装包后则加载样例
    `mode http`、`bind *:5000`（不监听 6443），`systemctl status` 可能显示 active，但 apiserver LB 不存在。
  - keepalived：加载样例 `/etc/keepalived/keepalived.conf`——实测样例含
    `state MASTER`、`interface eth0`、`virtual_router_id 51`、`auth_pass 1111`、
    VIP `192.168.200.16/17/18`。这会在宿主机网卡上尝试认领无关 VIP，形成网络污染风险；
    role 的 `track_script` / `notify_*` / 真实 `k8s_vip` 全部不生效。
- 测试为何没发现：`tests/ha/sandbox.yml:16-19` 置 `*_manage_service=false`，
  `tests/ha/test_ha_role.sh:378` / `:390` 用 `-f <渲染文件>` 手动启动；
  `tests/ha/test_ha_role.sh:109-110` 还静态断言 role 的 tasks/templates 中**不得出现**
  `/etc/haproxy` 或 `/etc/kubernetes`，等于反向禁止了正确路径。契约 §5.2 声明 systemd 未验证，
  但该声明只能说明“未验证”，不能使已知的错误路径变成可用实现。
- 建议方向（二选一，推荐前者）：
  1. 默认渲染到发行版路径：`haproxy_config_file=/etc/haproxy/haproxy.cfg`、
     `keepalived_config_file=/etc/keepalived/keepalived.conf`；保留 `*_root_prefix` 供沙箱重定向，
     并同步修改测试中的期望路径（`tests/ha/test_ha_role.sh:273-276`、`:378`、`:390`）。
  2. 保留 `/etc/kubernetes/*`，但由 role 写 systemd drop-in 覆盖有效配置：
     - haproxy：`/etc/systemd/system/haproxy.service.d/override.conf` 设 `Environment="CONFIG=..."`；
     - keepalived：drop-in 清空并重写 `ExecStart`，显式 `-f /etc/kubernetes/keepalived/keepalived.conf`；
     - 变更后 `daemon_reload` + restart。
  无论哪种，都要删除/覆盖包自带的样例配置，避免 keepalived 样例 VIP 被启动。

### [MAJOR] M1：`ha_mode=kube-vip` 渲染的静态 Pod 清单缺少运行必需项

- 位置：`roles/keepalived/templates/kube-vip.yaml.j2:8-27`
- 复现：`ha_mode=kube-vip` 渲染后检查清单；模板只有 `image` + `env`，没有：
  - `command: ["/kube-vip"]` / `args: ["manager"]`
  - kubeconfig 的 `volumeMounts` + `hostPath`（`cp_enable=true` 时 manager 需要）
  - `securityContext.capabilities.add: ["NET_ADMIN","NET_RAW"]`（VIP 操作必需）
- 期望：清单可直接放入 `/etc/kubernetes/manifests` 并由 kubelet 启动（至少静态结构完整）。
- 实际：容器没有 manager 子命令、没有 kubeconfig、没有网络权限；按 kube-vip 静态 Pod 约定无法工作。
  契约 §5.3 只承诺“配置渲染/漂移未验证”，但“渲染出的清单本身不可运行”仍属静态正确性缺陷。
- 建议方向：补齐 `command/args`、`securityContext`、kubeconfig 挂载（或明确改为 DaemonSet 方案），
  并在测试中增加对这些字段的断言；README 明确该清单需要集群侧 kubeconfig 路径。
