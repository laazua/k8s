## 7. 缺陷清单（本轮全部非阻塞）

### [MINOR] D1 A15 字面不成立：sandbox 两处 kubectl 直连无 `--request-timeout`
- 位置：`tests/e2e/smoke.sh:400`、`:407`（`"$KUBECTL" --kubeconfig ... auth whoami/can-i`）
- 复现：`grep -n '"\$KUBECTL" --kubeconfig' tests/e2e/smoke.sh`
- 期望：契约 A15 写「全部 kubectl 调用带 `--request-timeout`」；实际这 2 处缺失（`kctl`/`k` 均有）。
- 影响：低（本地 apiserver、`auth` 快速返回）；real 模式不符合面为零。
- 建议：改为 `kctl ... auth whoami`，一并复用 `--request-timeout`。

### [MINOR] D2 A12「计数不回退」未被自动化固化
- 位置：`tests/e2e/test_smoke_contract.sh:147`（`check "汇总 PASS>=15"`）
- 复现：把 sandbox 任一条 `ok` 改成 `skipped`，`PASS=29 SKIP=4` 时该断言仍绿（`SKIP=3` 断言会红，但若改成删除而非 SKIP 则不红）。
- 影响：契约 A12 明确要求 `PASS=30`，现仅靠评估者人工比对。
- 建议：`check_eq "汇总 PASS=30" 30 ...`（同样把 `FAIL=0` 已有断言保留）。

### [MINOR] D3 `k8s_service_cidr` 的 role-defaults fallback 是死代码
- 位置：`tests/e2e/smoke.sh:269` → `role_default roles/kube-apiserver/defaults/main.yml k8s_service_cidr`
- 事实：该 defaults 文件只有 `kube_apiserver_service_cluster_ip_range`（`roles/kube-apiserver/defaults/main.yml:107`），无 `k8s_service_cidr` 键 → fallback 永远取空。
- 影响：`group_vars/all/main.yml` 缺失该键时会 `FAIL 无法由 k8s_service_cidr 推导…`（**响亮失败**，非假绿），但契约 §3.4 宣称的回落路径不成立。
- 建议：fallback 改读 `kube_apiserver_service_cluster_ip_range` 并解掉 Jinja 默认，或删掉 fallback 并如实写进契约。

### [MINOR] D4 kubectl 不可执行被报成「API 不可达」；`kube-dns Service 存在` 对 rc=0 空输出放宽
- 位置：`tests/e2e/smoke.sh:439`（只判 `-z "$KUBECTL"`）、`:491`（`check` 只看 rc）
- 复现：`KUBECTL=/nonexistent/kubectl smoke.sh --mode real --kubeconfig X` → `FAIL API 不可达…`（实际是二进制不存在）
- 影响：诊断误导；判定方向正确（FAIL）。`svc` 检查理论上 rc=0+空输出即 PASS（真实 kubectl 不会，stub 才会）。
- 建议：`[[ -x "$KUBECTL" ]]` 前置 fail-fast；svc 检查断言输出含 `service/kube-dns`。

### [MINOR] D5 「缺值不打印 RESULT」只对 `--mode` 断言
- 位置：`tests/e2e/test_smoke_contract.sh:42-43`
- 事实：`--image`/`--kubeconfig`/`--mode --image x` 的 rc=2 有断言，无 RESULT 只有 `--mode` 一条。
- 影响：极低（三条共用 `need_val`，我在 §3 A1 已各自实测 RESULT 行=0）。
- 建议：循环断言四组 `(rc, RESULT 行数)`。

### [INFO] D6 `CD_SHA_MAP` 单条目
- 契约 §3.3/§9.6 已声明：新版本显式 FAIL 而非静默下载未校验制品。属有意取舍，非缺陷。

### [INFO] D7 sandbox 端口「检查后占用」存在 TOCTOU 窗口
- 位置：`tests/e2e/smoke.sh:285-286`（检查后到 `:337` 启动 apiserver 之间）
- 证据：我并行跑两个 sandbox 时第二个实例的端口检查可能先通过、启动时才暴露冲突（本次评估侧操作失误触发）。
- 影响：仅并发跑 e2e 时会互相干扰，单跑无影响；契约未要求并发。
- 建议（可选）：无需修；若将来并行化，改为启动失败即判 FAIL 的显式提示。
