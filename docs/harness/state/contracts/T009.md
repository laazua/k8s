## 1. 目标（本任务交付什么）

交付 `roles/kube-proxy`：用**官方二进制 + systemd** 在每个 node 上运行 kube-proxy，
使 `Service` 的 `ClusterIP` 可被真实访问。

- 安装官方 `kube-proxy`（强制 sha256；复用 `roles/download` 的缓存/代理）。
- 渲染 `KubeProxyConfiguration`（`kubeproxy.config.k8s.io/v1alpha1`）：
  `mode`、`clusterCIDR`、`bindAddress`、`healthzBindAddress`、`metricsBindAddress`、
  `conntrack`、`iptables`/`ipvs` 参数、`hostnameOverride`、`nodePortAddresses`
  全部变量化。
- 渲染 systemd unit（`Restart=always`、`LimitNOFILE`、`After=network-online.target`、
  `WantedBy=multi-user.target`），二进制/配置/unit 全部可由 `kube_proxy_root_prefix`
  重定向（测试沙箱）。
- kubeconfig：**消费**已存在的 kubeconfig（默认 `admin.conf` 作为引导凭据），或由
  `ca/cert/key` 渲染（证书内嵌）；落盘 `0600 root:root`。缺失/不可读 → 落盘前失败。
- fail-fast：`proxy_mode` 非法、`cluster-cidr` 缺失/非法、kubeconfig 缺失、
  iptables 依赖缺失、ipvs 模式但内核 `ip_vs` 未加载、二进制版本不匹配。
- 幂等：连跑两次第二次 `changed=0`，配置未变不重启（PID/starttime 不变）。

### 1.1 方案选择（必须声明）

**选择：二进制 + systemd（不使用 DaemonSet）。**

理由：

1. 当前环境 **docker registry 不可达**，无法拉取 kube-proxy 镜像，DaemonSet 无法真实运行，
   只能渲染未验证的 manifest；
2. 二进制方案可以**真实启动 kube-proxy 进程**并在 netns 内用真实 apiserver +
   真实 iptables 规则完成 ClusterIP 验收（A9），符合 spec C13「验收必须可执行」；
3. 二进制与项目「二进制部署」总目标一致，且与 T008 的 kubelet/containerd 交付形态一致。

DaemonSet 渲染分支**不在本任务交付**（若后续需要，另立任务并明确「未真实运行」）。

## 2. 非目标（明确不做什么）

- 不修改已 PASS 的 `roles/{base,download,pki,etcd,haproxy,keepalived,kube-apiserver,
  kube-controller-manager,kube-scheduler,containerd,kubelet}` 与其 tests。

  kubeconfig 或 `ca/cert/key`。

### 3.3 设计取舍（需 Evaluator 注意）

1. **kube-proxy 需要 Node 对象**：kube-proxy 1.31 启动时先 `GET /api/v1/nodes/<hostname>`；
   没有 Node 对象会持续重试而不启动 proxier。测试用 `kubectl` 手工创建 `node1`
   （`InternalIP=127.0.0.1`）——这是**测试夹具**，不是产品逻辑；真机上 kubelet 已注册节点。
   另需给 ClusterIP 一条 netns 内的 `lo` 路由（真实节点有默认路由）——同为测试夹具（§5.6）。
2. **EndpointSlice 而非 Endpoints**：kube-proxy 1.31 使用 EndpointSlice informer；
   没有 controller-manager 时手工 Endpoints 不会自动生成 EndpointSlice，故测试直接创建
   `discovery.k8s.io/v1` EndpointSlice（契约允许 Endpoints 或 EndpointSlice）。
3. **kubeconfig 来源**：role 支持两种模式：
   - `kube_proxy_kubeconfig_source`（默认 `{{ kube_proxy_config_dir }}/admin.conf`）→ 复制为
     `kube-proxy.conf`（0600 root:root）；
   - `kube_proxy_client_ca_file` / `cert` / `key` 全部存在 → 渲染内嵌证书的 kubeconfig。
   默认使用 admin.conf 是**引导期**选择（T007 已产出），生产应提供专用
   `system:kube-proxy` kubeconfig（T011 RBAC/附加组件任务）；role 不自行签发证书。
4. **iptables vs ipvs**：默认 `iptables`（环境已验证可用）；`ipvs` 分支完整渲染，
   但要求 `/proc/net/ip_vs` 存在，否则 fail-fast（本环境未加载 ip_vs，无法动态验证 ipvs）。
5. **healthz/metrics 安全默认**：均绑定 `127.0.0.1`；端口默认 10256/10249，测试覆盖为
   20249/20247，避免占用宿主默认端口。
6. **沙箱前缀**：`kube_proxy_root_prefix`（生产留空）把二进制/配置/kubeconfig/unit
   整体重定向；`kube_proxy_manage_service=false` 时不调用 systemctl。
7. **无镜像/无 Pod**：ClusterIP 的后端是 netns 内的本地 mock HTTP 服务
   （`10.0.0.10:18080`，非 loopback 因 EndpointSlice 拒绝 127/8），不是 Pod；
   这证明 kube-proxy 的 DNAT/转发数据面真实生效，但不证明 Pod 网络（T010）。

## 5. 受限声明（对应 spec R1 / C13）

### 5.1 systemd active/enabled 未在宿主真实执行（受限）

共享开发机禁止 `systemctl enable/start`、不写 `/etc/systemd/system`。因此：

1. role 的 `service.yml` 使用 `ansible.builtin.systemd`（可配置），默认 `true/started`；
2. unit 渲染到沙箱并断言全部关键项；
3. **用 unit 的 ExecStart 真实拉起 kube-proxy**，证明 unit 可直接执行；
4. 真机复验步骤见 §5.5。

### 5.2 单机 netns ≠ 多节点集群（受限）

测试在单机 netns 内验证「一个 kube-proxy 实例 + 一个 Service + 一个 EndpointSlice」的
ClusterIP 转发；不验证多 node 的 DaemonSet 调度、跨节点 Pod 网络（T010）或 NodePort/LB。
「kube-proxy 在全部 node 运行」在本任务由 **role 的 hosts 范围 + systemd enabled** 保证，
动态部分只证明单实例真实运行。真机复验见 §5.5。

### 5.3 未使用容器镜像 / 未运行 Pod（受限）

docker registry 不可达，无法起临时 Pod。ClusterIP 后端是 netns 内的本地 mock HTTP 服务
（`10.0.0.10:18080`；EndpointSlice 拒绝 loopback 地址），不是 Pod；因此本任务证明的是
kube-proxy 的 Service→Endpoint DNAT 数据面，不证明 Pod 网络/CNI。Pod 级 ClusterIP
访问属 T010/T011。

### 5.4 kube-proxy kubeconfig 使用引导凭据（受限）

默认 `kube_proxy_kubeconfig_source={{ kube_proxy_config_dir }}/admin.conf` 是 T007 的
引导凭据（cluster-admin）。生产应提供专用 `system:kube-proxy` kubeconfig（T011）；
本任务不修改 pki role 去签发该证书。测试动态验收使用 admin.conf，role 的
`ca/cert/key` 渲染分支由静态断言覆盖。
