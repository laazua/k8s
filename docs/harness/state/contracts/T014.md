## 1. 目标（本任务交付什么）

交付**真实的加节点入口** `playbooks/add-node.yml` + `roles/add-node`：对一台未初始化的新 worker
执行一条命令后，该节点由**真实 kubelet** 注册进既有集群（Node 对象存在、Ready 条件有可诊断
reason、kubelet.conf 身份 `system:node:<node>`、RBAC 允许 `get nodes` 且拒绝越权），**重复执行
`changed=0`**，且**既有控制面与既有节点零影响**（进程 PID 不变、配置/证书内容哈希不变、无重启）。

同时交付 `tests/add-node/` 真实验收套件（沙箱内真实 etcd + kube-apiserver + 两个独立
containerd/kubelet 实例），覆盖：注册、幂等、既有节点零影响、fail-fast、`--check`、宿主零污染。

## 2. 非目标（明确不做什么）

- 不实现升级/回滚（T015）、不实现端到端全流程文档（T016）。
- 不实现 CNI 安装（T010）与系统 Pod 真正 Running（无镜像，见 §5）。
- 不修改 `spec.md` / `roadmap.md` 验收定义；不修改任何已 accepted 的 role 语义。
- 不在宿主写 `/etc/kubernetes`、`/etc/systemd/system`；不 `systemctl start/stop` 除「本次新建的
  kubepods slice」以外的 unit；不占默认 6443/10250。
- 不做「把新节点加入 etcd 成员 / 控制面扩容」（README 只要求加 worker node）。

### 3.3 设计取舍（需 Evaluator 重点判断）

1. **新节点 = 独立 root 前缀的第二套运行时**：`$SB/node2` 独立 containerd（socket/state/root）
   与 kubelet（root-dir/端口 20251/20249/节点名 `node2`），与既有 `$SB/node1`（20250/20248）
   并存。两个实例共享宿主 cgroup（`kubepods.slice`），因此清理只停「本次运行新建」的 slice。
   这**不是**两台真实主机：不覆盖真实跨主机网络/磁盘隔离（§5）。沙箱没有 systemd：
   node1 的 containerd/kubelet 拆成两个 play（中间由测试从 unit 拉起 containerd）；
   node2 的 containerd 由 `sandbox_node2_containerd.yml` 预置并在 add-node 之前拉起
   （kubelet role 的 validate 要求 CRI socket 已存在；生产由 containerd 的 systemd 服务保证）。
2. **kubelet 证书在节点本地签发，但绝不重建 CA**：`add-node` 用 `pki` 的
   `tasks_from: cert` 只签发**本节点**一张 kubelet 证书（`CN=system:node:<node>`、
   `O=system:nodes`、SAN=节点名/地址/回环），并显式传 `pki_ca_rebuilt: {kubernetes: false}`
   让 pki 的幂等判定生效（否则 `default(true)` 会每次重签）。**不 include `pki:ca`**，
   且在 `validate` 阶段要求集群 CA 证书+私钥**已存在**（缺失即 fail-fast），
   运行后再断言 CA 证书/私钥内容哈希未变。→ 「不得重建 CA」既有静态断言也有动态哈希断言。
   安全上提供 `add_node_cert_mode: preissued`（默认 `sign`）：`preissued` 要求节点上已有由
   控制面签发的 kubelet 证书，节点**无需 CA 私钥**；真机推荐用法见 §5。
3. **kubelet.conf 由 `roles/kubelet` 渲染，不调用 `roles/cluster-addons`**：`cluster-addons`
   的 `facts.yml` 会 `slurp` **admin 证书+私钥**才能渲染，把 admin 凭据带上 worker 违反最小权限。
   `roles/kubelet` 的 `kubelet:kubeconfig` 渲染同一语义（内嵌 CA+leaf、0600 root:root、
   只含 kubelet 身份），故复用 `kubelet` role；测试额外断言**新节点根下没有 admin.conf**。
   这是对任务提示「cluster-addons（kubelet.conf）」的**有意偏离**，理由如上，请独立判断。
4. **注册校验（`add-node:verify`）在控制端执行**：`delegate_to: localhost`（可配
   `add_node_verify_delegate`），用运维侧 `kubectl` + `admin.conf` 读 `node/<new>` 的
   Ready 条件。worker 上不需要也不应有 admin 凭据。缺 kubeconfig/kubectl → fail-fast。
5. **顺序由 playbook 显式表达**：`roles: [base, add-node, containerd, kubelet]` +
   `post_tasks: add-node:verify`，测试用 `--list-tasks` **断言顺序**（validate → cert →
   containerd → kubelet → verify），而不是只断言「非空」。
6. **幂等实现**：证书走 pki 的 `_needs_regen`（有效且匹配 → 不动）；kubelet.conf/config/
   unit 走 `template`（内容相同 → 不 changed、不 notify handler）；containerd 同理。
   第二次运行**不重启** kubelet（沙箱 PID 不变、Node 对象 UID 不变）。
7. **fail-fast 清单**：目标主机不在 `add_node_target_group`（`k8s_node`）→ 拒绝；
   集群 CA 证书缺失 / `sign` 模式下 CA 私钥缺失 → 拒绝且**不生成**新 CA；
   `preissued` 模式下缺证书 → 拒绝；kubelet 版本与集群 minor 不兼容（可配
   `add_node_allow_minor_skew`）→ 拒绝；`verify` 开启但 kubeconfig/kubectl 不可用 → 拒绝。

## 5. 受限声明（对应 spec R1 v1.4 / C14）与真机复验

1. **系统 Pod 不会 Running**：无镜像（`registry.invalid`），只断言清单渲染 + 对象/RBAC/SA 存在。
2. **「新节点」是同一宿主上的第二套运行时**：独立 root/端口/节点名，共享内核与 cgroup；
   不覆盖真实跨主机网络、磁盘、kubelet 心跳抖动与真实多主机 join 失败域。
3. **沙箱不跑 base**：`base` 的 swapoff / sysctl / 主机名任务在共享开发机属破坏性操作，
   沙箱以 `add_node_manage_host=false` 整体跳过 base role（真机默认 `true`，真实执行
   `base:files` + `base:system`）。
4. **沙箱以 root 预置 CA**：`sign` 模式要求节点上有 CA 私钥；沙箱把集群 CA 证书+私钥
   复制到 `$SB/node2/etc/kubernetes/pki/` 模拟运维分发。**生产推荐 `preissued`**（见下）。
5. **沙箱不启 systemd**：`containerd_manage_service=false` / `kubelet_manage_service=false`，
   进程由测试从 role 渲染出的 unit `ExecStart` 拉起；node1 拆成 containerd/kubelet 两个 play，
   node2 的 containerd 在 add-node 之前预置并拉起（与 add-node 同一 role/变量，首跑 containerd
   段 `changed=0`）。「handler 重启」路径未在沙箱验证。
6. **沙箱 kubelet 放宽磁盘驱逐阈值**：宿主根盘余量 <15% 会触发 `DiskPressure`（T013 教训），
   仅测试用 `--eviction-hard=imagefs.available<1%,nodefs.available<1%,...`（§9），
   不进入 `roles/kubelet` 默认值，不放宽任何断言。
7. **真机复验步骤**：

```bash
# 0) 前置：控制面已可用；新节点已进 inventory 的 [k8s_node]，且已被 base/download 预置
#    （二进制制品、containerd、swap 关闭、内核模块）；运维把集群 CA 证书分发到节点
#    /etc/kubernetes/pki/ca.crt（推荐 preissued：把控制面签发的 kubelet 证书也分发到位）。
cp inventory/hosts.example inventory/hosts.yml   # 按实际主机填写

# 1) 推荐路径（节点上无 CA 私钥）：控制面签发 → 分发 → 节点侧装配
ansible-playbook -i inventory/hosts.yml playbooks/add-node.yml -l <new-node> \
  -e add_node_cert_mode=preissued
kubectl get node <new-node> -o wide     # 期望 Ready=True（有 CNI 时）
kubectl get pods -A -o wide | grep <new-node>   # 期望系统 Pod 在该节点 Running

# 2) 简单路径（CA 私钥可安全下发时，默认 sign 模式）
ansible-playbook -i inventory/hosts.yml playbooks/add-node.yml -l <new-node>

# 3) 幂等复跑（应 changed=0 且不重启 kubelet）
ansible-playbook -i inventory/hosts.yml playbooks/add-node.yml -l <new-node>
systemctl show kubelet -p ActiveEnterTimestamp   # 期望与上一跑一致

# 4) 既有节点零影响抽查
kubectl get nodes -o wide
```

## 7. 风险与假设

- 双 kubelet 共享 `kubepods.slice`：清理只停本次新建 slice，若宿主已有同名 slice 则不动。
- pki 的 `cert.yml` 依赖 `pki_ca_rebuilt` 缺省为 true（会每次重签）→ add-node 必须显式传
  `{kubernetes: false}`；这是幂等的关键接线，已加静态断言。
- `--check` 的覆盖面取决于既有 role 的 check-mode 洁净度：`add-node` 的只读判定
  （分组/CA/版本/证书是否已存在）在 check 模式下真实执行（`check_mode: false`）；
  `containerd`/`kubelet` 在 check 模式下整体跳过——两者的 validate 依赖只读 `command`
  （openssl / `--version`），Ansible 在 check 模式会跳过 command 导致误判，故不强行复用。
  这是**声明的覆盖面限制**（§9），不是静默降级；`--check` 仍断言 rc=0/changed=0/产物哈希不变。

1. **系统 Pod 未 Running**：无 registry/镜像（`registry.invalid`），B7 只断言清单可 apply +
   对象/SA/Deployment/ConfigMap 存在；Running 相关断言以 SKIP 单列（SKIP=2，不计入 PASS）。
   真实 CNI 就绪后的 Ready=True / 系统 Pod Running 需真机复验（§5.7）。
2. **单宿主双运行时**：node1/node2 是同一宿主上的两套独立 root/端口/节点名，共享内核与
   cgroup。**不覆盖**真实跨主机网络、磁盘、时钟、kubelet 心跳抖动与多主机失败域。
3. **未启 systemd**：`*_manage_service=false`，进程由测试按 role 渲染的 unit `ExecStart`
   拉起。因此 **handler 触发的 kubelet/containerd 重启路径未在沙箱验证**（幂等断言的是
   「不重启」，即 PID 不变，可验证）。
4. **沙箱不跑 base**：`add_node_manage_host=false` 跳过 base（swapoff/sysctl/hostname 在共享
   开发机属破坏性）。真机默认 `true`，`base:files` + `base:system` 路径未在沙箱覆盖。
5. **CA 分发是模拟的**：沙箱把集群 CA 证书+私钥复制到 `$SB/node2/etc/kubernetes/pki/`，
   以覆盖默认 `sign` 模式；**生产推荐 `preissued`**（私钥不出控制面）。`preissued` 模式的
   失败路径由 D4 覆盖，成功路径未端到端跑（沙箱主路径用 sign）。
6. **`--check` 覆盖面有限（声明，不静默）**：`add-node` 自身只读判定在 check 模式真实执行
   （`check_mode: false`），`containerd`/`kubelet` 在 check 模式整体跳过（其 validate 依赖
   只读 `command`，check 模式下会被跳过而误判）。D7 断言的是 rc=0/changed=0/产物哈希不变/
   无 `from_json`，**不等价于**「全部 role 的 check 模式洁净」。
7. **kubelet 磁盘驱逐阈值放宽仅限测试**：`--eviction-hard=...<1%` 通过 `kubelet_extra_args`
   注入沙箱（T013 教训：宿主根盘余量 <15% 会触发 DiskPressure），**未改 `roles/kubelet`
   默认值**，也未放宽任何断言。
8. **未做独立 mutation campaign**：牙齿证据为内建的自检 + 定向篡改（见 §10），不是系统化
   变异测试；93 条红来自「role 缺失」这一粗粒度变异，对「实现细节错误」的检出强度需
   Evaluator 自行复核。
9. **未做多节点串行验证**：`serial: 1` 只做了静态断言 + 单节点行为验证，两台以上新节点
   依次加入的批次行为未实测。

**已内建的「牙齿」证据（建议优先复核）**：

1. **B7 篡改—复原**：测试在 node2 收敛后故意改写 `kubelet.conf`，重跑必须 `changed>0`
   并复原内容 → 证明「changed=0」不是恒真断言。

3. **fail-fast 6 组（D1–D6）**：非 `k8s_node` 主机、缺 CA 证书、sign 缺 CA 私钥、preissued

   **未落盘/未生成新 CA**。
4. **零影响是显式 FAIL**：node1 kubelet / apiserver / etcd 的 PID 与启动时间、node1 配置/
   证书哈希、Node 对象 UID 均为 `check_eq`（空值重试后 FAIL），不是 `|| true`。
