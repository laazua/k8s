# 任务契约 · T015

- 任务标题：版本升级与回滚（升级前自动备份 etcd/证书）
- 契约状态：`ready_for_eval`（实现与自测完成，待 Evaluator 独立验证）
- 负责人（Generator）：harness-generator（子代理会话）
- 复核（Evaluator）：harness-evaluator
- 更新时间：2026-11-18

## 1. 目标（本任务交付什么）

交付**真实的升级/回滚入口** `playbooks/upgrade.yml` + `roles/upgrade`：

1. 用一条命令把集群从 1.31 升到相邻 minor（1.32），**升级前自动备份** etcd 数据快照
   （真实 `etcdctl snapshot save`）+ PKI/证书目录 + kubeconfig + 旧二进制，落到**带时间戳目录**，
   目录内有 `MANIFEST.txt` 与 `SHA256SUMS`；**备份失败立即中止**，不继续升级。
2. 升级后：`kubectl get --raw /version` 的 `gitVersion` = 目标版本、`kubelet --version` = 目标版本、
   节点仍注册且 Ready 条件存在（真机为 Ready=True）。
3. 按文档命令回滚：恢复上一版本二进制 + etcd 快照 + 证书，`/version` 回到原版本、`/healthz=ok`、
   节点仍注册；回滚前后内容哈希可证、升级期间写入的集群数据在回滚后消失（证明 etcd 真的回退）。
4. 幂等：已在目标版本时重跑 `changed=0`（不重复备份、不重启）。
5. fail-fast：非法版本格式、跨多个 minor（无 force）、无备份/备份缺 sha256/备份被篡改却请求回滚、
   目标二进制 sha256 不符 → 全部拒绝且不产生副作用。

同时交付 `tests/upgrade/` 真实验收套件（单宿主沙箱：真实 etcd + apiserver + containerd + kubelet +
CM/scheduler 渲染），覆盖上述全部条目 + `--check` + 宿主零污染。

## 2. 非目标（明确不做什么）

- 不实现端到端全流程文档（T016）、不改 CNI/调度/加节点语义。
- 不做跨多个 minor 的实际升级（只做**门禁**：默认拒绝，需显式 `-e upgrade_allow_minor_jump=true`）。
- 不做自动回滚（回滚是显式动作 `-e upgrade_action=rollback`）。
- 不修改 `spec.md` / `roadmap.md` 验收定义；不修改任何已 accepted 的 role 语义。
- 不在宿主写 `/etc/kubernetes`、`/etc/systemd/system`；不 `systemctl start/stop` 业务 unit。
- 不实现「无 systemd 时的进程重启」（沙箱由测试按 unit `ExecStart` 拉起，见 §5）。

### 3.3 设计取舍（请 Evaluator 重点判断）

1. **角色 `upgrade` 同时承载 upgrade 与 rollback**，由 `upgrade_action`（`upgrade|rollback`）分派；
   playbook 是唯一入口（`hosts: k8s_master` 控制面滚动 + `hosts: k8s_node` 工作节点滚动，均 `serial: 1`）。
   rollback 复用同一 role 的变量与 verify，避免两套判定漂移。
2. **「已安装版本」以本机二进制 `--version` 为准，集群 `/version` 只作交叉校验**：
   `upgrade_version_probe_component = upgrade_components | first`（控制面 kube-apiserver / 节点 kubelet）。
   只在**两者都等于目标**时短路（`changed=0`、不备份、不重启）。这样「二进制被换回旧版」也能被
   重跑纠正（内建牙齿，见 §10），而不是靠集群版本「看起来对」就跳过。
3. **备份是升级的前置条件，不是尽力而为**：`backup.yml` 内 `assert` 快照非空、`SHA256SUMS`
   存在且 `sha256sum -c` 通过、文件数达标；任一失败 → play 中止（默认 fail 语义），
   后续 `binaries.yml` 不会执行（测试断言「安装的二进制仍是旧版」）。
4. **备份目录按主机 + 时间戳隔离**：`<backup_root>/<UTC 时间戳>-<inventory_hostname>/`，
   含 `bin/`（旧二进制）、`pki/`（整棵证书树）、`kubeconfigs/`（或节点 kubelet.conf/config.yaml）、
   `etcd-snapshot.db`、`MANIFEST.txt`、`SHA256SUMS`。目录 0700（含私钥）。
5. **etcd 回滚是真恢复，不是拷文件**：`etcdctl snapshot restore` 到新目录 → 校验 `member/snap/db`
   → 把现数据目录改名为 `<data_dir>.pre-rollback-<ts>`、把恢复目录换入 → 恢复属主/权限。
   沙箱无 systemd，故要求显式 `-e upgrade_rollback_etcd_offline_ack=true` 表示「etcd 已停止」，
   否则拒绝替换数据目录（防止对活着的 etcd 换数据目录）。生产 `upgrade_manage_service=true`
   时由 role 自己 stop/start。
6. **沙箱的「重启」由测试执行**（与 T014 同一范式）：role 只安装二进制 + `notify` handler；
   `upgrade_manage_service=false` 时 handler 不执行，测试按 unit `ExecStart` 重新拉起进程，
   再断言 `/version`。因此 `upgrade_verify_cluster_version` 在沙箱置 `false`（role 内无法重启），
   **但同一断言由测试在重启后真实执行**，并在 §5/§9 显式声明该覆盖面差异。
7. **Ready 判定双模式**：`upgrade_require_ready_nodes=true`（生产默认）要求 `Ready=True`；
   沙箱置 `false`（无 CNI），此时仍要求 Ready **条件存在**且 `False` 时 `reason` 非空。
   两种模式都有断言；沙箱额外跑一次 `require_ready=true` 期望**失败**（证明该判定有牙齿）。
8. **minor 门禁**：`target_minor - current_minor > 1` 且 `upgrade_allow_minor_jump=false` → 拒绝；
   `target < current` 且 `upgrade_allow_downgrade=false` → 拒绝。门禁用 `--tags upgrade:validate`
   单独驱动，不触发下载/备份（测试零网络）。

## 5. 受限声明（spec R1 v1.4 / C14）与真机复验

1. **单宿主单节点**：「全部节点 Ready」在沙箱是 node1 一个节点 + cp1（控制面不注册 Node 对象时
   不参与）；真实多节点滚动（`serial: 1`）与「全部节点」需真机。
2. **无 CNI → NotReady**：`upgrade_require_ready_nodes=false` 时只断言 Ready 条件存在 + reason 非空；
   `true` 模式在沙箱必然失败（B7 反向证明判定真实）。真机 Ready=True 见下。
3. **无 systemd**：`upgrade_manage_service=false`，role 不 stop/start；测试按 unit `ExecStart`
   重新拉起进程。**handler 重启路径与 `systemctl` 语义未在沙箱验证**。
4. **`upgrade_verify_cluster_version=false`（沙箱）**：role 无法重启进程，故 role 内只断言
   「已安装二进制版本 = 目标」；`/version` 的断言由测试在重启后真实执行（同一断言，不同执行者）。
5. **etcd 回滚需显式确认离线**：沙箱用 `upgrade_rollback_etcd_offline_ack=true` + 测试先停 etcd；
   生产的 stop/start 由 role 的 handler/任务在 `upgrade_manage_service=true` 下完成。
6. **etcd 为单成员**：3 成员集群的滚动重启、成员间数据一致性、快照 restore 后的集群重建未验证。
   多成员回滚必须显式覆盖（与 `roles/etcd` 的 `etcd_member_name: "{{ inventory_hostname }}"` + TLS peer 对齐）：
   `-e upgrade_rollback_etcd_member_name=<inventory_hostname>`
   `-e upgrade_rollback_etcd_initial_peer_url=https://<peer_ip>:2380`
   `-e upgrade_rollback_etcd_initial_cluster='<name>=https://<peer_ip>:2380,...'`（T019 D7 补齐）。
7. **kubelet 磁盘驱逐阈值放宽仅限测试**（宿主根盘余量 <15%，T013 教训），不改 role 默认值。
8. **真机复验步骤**：

```bash
# 0) 前置：集群 Ready、inventory 的 [k8s_master]/[k8s_node]/[etcd] 填写完毕；
#    /usr/local/bin/etcdctl 可用；控制面 PKI 与 admin.conf 就位。
cp inventory/hosts.example inventory/hosts.yml

# 1) 干跑（不落盘）：应 rc=0、changed>0
ansible-playbook -i inventory/hosts.yml playbooks/upgrade.yml -e k8s_version=1.32.13 --check

# 2) 升级（控制面滚动 → 工作节点滚动；serial: 1）
ansible-playbook -i inventory/hosts.yml playbooks/upgrade.yml -e k8s_version=1.32.13

# 3) 验证
kubectl get --raw /version                  # 期望 gitVersion: v1.32.13
kubectl get nodes -o wide                   # 期望全部 Ready=True 且 VERSION=v1.32.13
ls /var/backups/kubernetes/upgrade/         # 期望 <时间戳>-<主机名>/（含 etcd-snapshot.db/SHA256SUMS）

# 4) 幂等复跑：期望 changed=0、不产生新备份目录、不重启
ansible-playbook -i inventory/hosts.yml playbooks/upgrade.yml -e k8s_version=1.32.13

# 5) 回滚（先停控制面/etcd 由 role 负责；显式指定备份目录）
systemctl stop kube-apiserver kube-controller-manager kube-scheduler kubelet
ansible-playbook -i inventory/hosts.yml playbooks/upgrade.yml \
  -e upgrade_action=rollback -e upgrade_rollback_dir=/var/backups/kubernetes/upgrade/<ts>-<host>
kubectl get --raw /version                  # 期望回到 v1.31.0
kubectl get --raw /healthz                  # 期望 ok
kubectl get nodes                           # 期望节点仍注册（Ready=True）
```

## 7. 风险与假设

- 沙箱升级需要 1.31.0 与 1.32.13 两套官方制品；1.32.13 由测试预取（含官方 `.sha256`），首跑慢。
- 备份复制约 300 MB 二进制 ×2 套（控制面 + 节点）；`/tmp` 需 ≥ 3 GB 余量。
- `etcdctl snapshot restore` 的成员名必须与数据目录一致，故 `upgrade_rollback_etcd_member_name` 可配。
- 沙箱 node1 的 kubelet 在 etcd 回滚期间会被停止/重启；Node 对象来自回滚后的快照（升级前已注册），
  因此「仍注册」是真实断言而非残留。

## 10. 给 Evaluator 的提示（牙齿与复现）

**优先复核的 6 颗牙齿**（都应「红」）：

| 牙齿 | 命令/操作 | 期望 |
| --- | --- | --- |
| B8 Ready 判定 | `--tags upgrade:verify -e '{"upgrade_verify_cluster_version":false,"upgrade_require_ready_nodes":true}'` | rc≠0，日志含 Ready |
| C2 自愈 | 把 `kube-scheduler` 换回 1.31 后重跑 | rc=0 且 `changed>0`，版本回到 1.32.13；再跑 `changed=0` |
| E6 备份篡改 | 复制真实备份后改 `bin/kube-apiserver` 再回滚 | rc≠0，sha256 校验失败；已安装二进制未变 |
| E7 制品 sha | `file://` 假制品 + 官方 sha | rc≠0，已安装/假 bin 均未落盘 |
| E8 制品版本 | 假制品 + 注入匹配 sha（落到假 bin 目录） | rc≠0，版本断言失败；真实 bin 未变 |
| B5 备份失败中止 | 错误 etcd endpoints | rc≠0，已安装 apiserver 仍 1.31.0、无完整备份 |

**复现**：


**易误判点**：

- `--check` 的 `changed>0` 来自 `component.yml` 的「计划变更」debug（`changed_when:
  upgrade_component_needs_change`），不是真实写入；`--check` 不创建备份目录、不改二进制。

  D4 的 ConfigMap 消失是 etcd 真回退的独立证据。
