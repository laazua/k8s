## 1. 目标（本任务交付什么）

交付 `roles/cilium`：用 **Jinja 模板离线渲染** Cilium 部署清单（不拉 chart、不拉镜像），
把版本、模式（默认 VXLAN）、`kubeProxyReplacement=false`（保留 kube-proxy）、集群名/ID、
Pod CIDR、API endpoint、MTU、tunnel 端口、资源与容忍、镜像仓库前缀全部变量化；
渲染落盘支持沙箱前缀（生产留空）。

同时交付 `tests/cilium/`：静态/渲染断言 + **netns + veth + VXLAN 双节点真实拓扑**，
按 role 渲染出的 VNI（Cilium `cluster-id`）、tunnel 端口、MTU 建立内核隧道，
验证跨 netns ICMP/HTTP，并用 VNI/端口不一致做失败反证。

### 1.1 方案选择（必须声明）

**选择：role 内 Jinja 模板直接渲染 Kubernetes 清单（multi-doc YAML）。**

理由：

1. 当前环境 **registry 不可达、无任何镜像**，`helm install`/DaemonSet/Pod 均无法真实运行；
   spec R1（v1.4）要求把验收下沉到「渲染产物 + 真实内核对象」，而不是伪造 `cilium status`。
2. 纯 `ansible.builtin.template` 渲染**不需要外网**，满足离线/密闭要求；`--check`、
   `--list-tasks` 天然可用。
3. VXLAN 数据面可用 `netns + veth + ip link add type vxlan` **真实建立**，参数直接取自
   渲染后的 `ConfigMap`，从而把「变量映射」和「数据面」连起来。
4. 不引入 helm 二进制/网络 chart，避免「离线可渲染」的假绿风险。

### 3.3 设计取舍（需 Evaluator 注意）

1. **VNI 语义**：Cilium 以 `cluster-id` 作为 VXLAN VNI（官方 agent 无独立 `vxlan-id` 选项）。
   因此模板渲染 `cluster-id`，测试把它直接当 VNI 建隧道。`cluster-id` 范围按 24-bit VNI 校验。
2. **ConfigMap key**：使用 Cilium agent 的 configmap 键名（`routing-mode`、`tunnel-protocol`、
   `tunnel-port`、`mtu`、`cluster-name`、`cluster-id`、`cluster-pool-ipv4-cidr`、
   `k8s-service-cidr`、`k8s-service-host`、`k8s-service-port`、`kube-proxy-replacement`）。
3. **operator**：默认渲染 `cilium-operator` Deployment + 独立 SA/ClusterRole(Binding)；
   可用 `cilium_operator_enabled=false` 关闭。它不会被运行（无镜像）。
4. **沙箱前缀**：`cilium_root_prefix`（生产留空）把清单整体重定向；
   测试只写 `mktemp -d` 沙箱。
5. **无 CLI 依赖**：role 不使用 `kubectl`/`helm`/`cilium` CLI；只渲染文件。

## 5. 受限声明（对应 spec R1 / C13）

### 5.1 cilium-agent 未运行（受限）

无镜像/registry 不可达，`cilium-agent` 与 `cilium-operator` **未启动**。因此
`cilium status`、agent healthz、BPF maps 均未验证。role 只保证**清单可渲染、可解析、
变量一致**；运行态属真机复验（§5.7）。

### 5.2 Pod 网络未验证（受限）

没有容器运行时镜像，无法创建 Pod。B4 的连通性来自 **netns 内的内核 VXLAN 隧道**
（两个 netns 模拟两个节点），不是 Cilium 的 Pod 网络；不验证 IPAM、Endpoint、策略、
BPF 转发。**不得**把 B4 表述为「Pod 跨节点通信已验证」。

### 5.3 `cilium status` / Node Ready 未验证（受限）

无 kubelet 注册的真实 Node（T008 的真机验收不在本任务），且 agent 未运行，
故 `kubectl get nodes` 的 `Ready`（Cilium 负责的 CNI 条件）与 `cilium status --wait`
未验证。真机步骤见 §5.7。

### 5.4 内核 VXLAN ≠ Cilium BPF 数据面（受限）

B4 证明的是：**渲染出的 VNI/端口/MTU 能被真实内核用来建立可用隧道**，且参数不一致会
真实失败。它**不**证明 Cilium 的 BPF 封装/解封装、identity、policies、kube-proxy
replacement、DSR 等行为。二者只共享 VXLAN 封装参数这一层。

### 5.5 operator/hubble/CRD 未验证（受限）

模板渲染 operator Deployment 与 RBAC，但不运行；CRD、hubble、服务网格等不在本任务
最小交付内（见 §2）。

### 5.6 `vxlan` 内核模块为环境前置（受限）

套件**不主动** `modprobe`/`rmmod`，以免改宿主内核模块状态。启动时检查
`/sys/module/vxlan`；缺失则显式失败并提示「需由环境预置 vxlan 模块」。
如需在干净环境临时允许加载，可显式设置 `CILIUM_TEST_ALLOW_MODPROBE=1`（默认关闭），
套件才会执行一次 `modprobe vxlan`，并在 §8 记录。

### 10.3 r2 修复：fail-fast 条件写反（产品 bug）+ 自相矛盾用例

**现象**：全量 `make test` 中 cilium 套件 `221/8`，8 条失败全部集中在 B1b geneve 变体；
`t010_variant_geneve.log` 显示 validate 以「replacement=true 但 kube-proxy 未启用」失败，
而 B1b 传入的正是**合法组合** `replacement=true + enabled=false`。

**根因**：
1. `roles/cilium/tasks/validate.yml` 断言写成
   `not (replacement and not enabled)` → 把合法组合判为冲突，语义完全反了；
2. `tests/cilium/test_cilium_role.sh` 的 conflict 用例同样传入
   `replacement=true + enabled=false` 并期待失败 → 与 B1b 自相矛盾，掩盖了产品 bug。

**修复**（TDD：先由 B1b 红暴露，再改实现）：
- 断言改为 `not (replacement | bool and enabled | bool)`：仅当**两者同时启用**才冲突；
  fail_msg 与任务名同步修正（`replacement=false` 或 `enabled=false` 二选一）。
- conflict 用例改为 `replacement=true + enabled=true`，描述更新为「replacement=true 且 kube-proxy 仍启用」。
- 契约 §4 B2 措辞同步。

**证据**：修复后 `make test-cilium` 连跑两次 **229/0**（rc=0，逐条一致）；
全量 `make test` rc=0（1633）。
