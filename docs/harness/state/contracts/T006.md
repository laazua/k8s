## 1. 目标（本任务交付什么）

`roles/haproxy` + `roles/keepalived`：为控制面 apiserver 提供 **VIP + TCP 负载均衡**。

- `roles/haproxy`：从 inventory 的 `[k8s_master]` 推导后端，渲染 `haproxy.cfg`
  （`mode tcp`、`balance`、每个 master 的 `server <host> <ip>:<port> check`、timeouts），
  包安装/二进制断言、systemd enable/start、配置变更才重启。
- `roles/keepalived`：VRRP VIP（`vrrp_instance`、`state`、`priority`、`virtual_router_id`、
  `virtual_ipaddress = k8s_vip`、`interface`、`track_script`、`notify_*`），
  `track_script` 检查**本机** haproxy pid 文件；`ha_mode=kube-vip` 分支渲染 kube-vip 静态 Pod
  清单并做前置校验（**真实漂移未验证**，见 §5）。
- 可判定验收（roadmap）：VIP 可达且 `curl -k https://<VIP>:6443/healthz` 返回 ok；
  停掉持有 VIP 的 master 后 VIP 漂移到另一 master 且仍返回 ok。

## 5. 受限声明（对应 spec R1 / C13）

### 5.1 真实 VRRP 但非多机（已尽量逼近）
- **已验证**：Linux VRRP 协议（raw socket、advert、priority 选举、gratuitous ARP）、VIP 的真实
  `ip addr add/del`、真实 haproxy 进程转发、真实 TLS 后端、真实健康检查摘除。
- **未验证**：跨物理交换机/真实网卡、防火墙放行 VRRP（协议号 112）、云环境 ARP/BGP 限制、
  多主机时钟/网络抖动。netns 共享同一内核，不能等价于多机 HA。
- **真机复验**（必做）：
  ```bash
  # 3 台 master（inventory [k8s_master]），先确保 VRRP 112 与 VIP 网段互通
  ansible-playbook -i inventory/hosts.ini playbooks/control-plane.yml --tags 'haproxy,keepalived'
  # 在任一节点：
  curl -k https://<VIP>:6443/healthz            # 期望 ok
  ip -4 addr show dev <k8s_vip_interface> | grep <VIP>
  # 停掉当前 MASTER 的 keepalived+haproxy（或整机下电）：
  sudo systemctl stop keepalived haproxy         # 只在持有 VIP 的节点执行
  # 在另一节点观察：
  watch -n1 'ip -4 addr show dev <k8s_vip_interface> | grep <VIP>'
  curl -k https://<VIP>:6443/healthz              # 期望仍 ok
  # 恢复该节点：
  sudo systemctl start haproxy keepalived         # 期望 priority 高者 preempt 回切
  ```
  期望：VIP 在 `3*advert_int + skew` 内漂移；回切后原 MASTER 重新持有 VIP。

### 5.2 systemd / 包安装未验证
- 测试用解包二进制直接启动（`haproxy -D`、`keepalived -P -n`），**未验证** `package` 安装与
  systemd unit 的 enable/start/restart。role 的 systemd 分支由 `haproxy_manage_service` /
  `keepalived_manage_service` 控制，测试置 false；handler 只在配置/脚本内容变化时通知。
- 真机复验：`systemctl status haproxy keepalived`、`systemctl is-enabled ...`、改优先级后重启并观察 VIP。

### 5.3 kube-vip 仅配置渲染
- `ha_mode=kube-vip` 只渲染静态 Pod 清单并校验 VIP/网卡/镜像；**未验证**镜像拉取、Pod 启动、
  ARP/BGP 漂移、选主。契约与 README 均显式声明，不得表述为「已验证生效」。
- 真机复验：在真实集群应用清单，`kubectl -n kube-system get pod -l name=kube-vip`，
  停掉持有 VIP 的节点，确认 VIP 漂移与 apiserver 可达。

### 5.4 同机 haproxy 与 apiserver 端口协调（T007）
- 本 role 默认 `haproxy_lb_port = haproxy_backend_port = 6443`（面向独立 LB / 客户端）。
  若 haproxy 与 kube-apiserver 同机，二者不能同时绑定 `0.0.0.0:6443`。T007 必须二选一：
  apiserver 仅监听 `127.0.0.1:6443`，或 haproxy 使用独立前端端口。
  **本任务不验证**该组合，只保证两个端口变量可独立配置。

### 5.5 T005 遗留（etcd 重启）
- 本 role 不重启 etcd；若 T007/T012 编排中包含 etcd 重启，必须按 T005-r2 的 MINOR 显式加 `serial: 1`。
  已在 handoff 标注。

## 7. 风险与假设
- 假设 master 在同一 L2，且 VRRP（112）与 VIP 未被云厂商/防火墙阻断；否则改用 kube-vip（仅渲染，需真机）。
- 假设 `k8s_master` 分组非空且每台有可路由的 `ansible_host`；否则 role fail-fast。
- 风险：同机 6443 端口冲突（§5.4），由 T007 决定监听模型。
- 风险：keepalived `enable_script_security` 要求脚本与父目录 root 拥有、不可被 group/other 写；
  生产 role 以 root 运行时满足，测试用 `/run` 安全目录满足。
