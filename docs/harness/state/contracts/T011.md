## 1. 目标（本任务交付什么）

交付 `roles/cluster-addons`：从 `roles/pki` 的产物渲染并安装 **kubeconfig**、渲染 **RBAC**
与 **CoreDNS** 清单（含 Corefile），全部路径/域名/端口/版本/镜像仓库/上游可变量化，
支持沙箱前缀（生产留空）。

同时交付 `tests/cluster-addons/`：静态断言 + **真实 TLS etcd + kube-apiserver**
下的 kubeconfig 认证与 RBAC 正反例 + **CoreDNS 官方二进制**按渲染出的 Corefile
真实解析（kubernetes 插件 + 上游转发）+ 反证（域变量真实生效）+ 密闭性/宿主零污染。

### 1.1 方案选择（必须声明）

**选择：role 只渲染/安装文件，不在本机运行 CoreDNS Pod。**

理由：

1. 本环境 **registry 不可达、无任何镜像**（spec R1 v1.4），`kubectl apply` 后的
   Deployment 无法拉起 Pod；伪造「CoreDNS Running」不可接受。
2. kubeconfig 与 RBAC 的正确性可以**真实验证**：沙箱内拉起真实 TLS etcd 与
   kube-apiserver，用渲染出的 `admin.conf` / `kubelet.conf` 真正认证并跑
   `kubectl auth can-i` 正反例。
3. Corefile 的语义可以用 **CoreDNS 1.11.3 官方二进制**（sha256 固定，缓存）真实执行：
   `kubernetes` 插件连沙箱 apiserver 解析真实 Service、`forward` 转发到测试 DNS mock。
   这验证的是同一份渲染产物，不是仿真。
4. 不引入 helm/kustomize 依赖；纯 `ansible.builtin.template`，离线可渲染。

### 3.2 环境事实（2026-11-11 实测）

| 探测 | 结果 | 结论 |
| --- | --- | --- |
| docker registry / 镜像 | 不可达 / 无镜像 | CoreDNS 不运行 Pod |
| `dl.k8s.io` | 可用 | kubectl / kube-apiserver 制品 |

### 3.3 设计取舍（需 Evaluator 注意）

1. **kubeconfig 内嵌证书**：`certificate-authority-data` / `client-certificate-data` /
   `client-key-data` 均为 base64 内嵌（便于分发、不依赖路径），文件 `0600 root:root`。
   `no_log: true` 防止私钥进日志。
2. **默认不覆盖**：`ansible.builtin.template` 的 `force` 绑定
   `cluster_addons_rotate_kubeconfigs`（默认 `false`）。重跑不覆盖既有 kubeconfig；
   证书轮换时显式置 `true`。**这是刻意行为**，B3 专门验证（写入 MARKER → 不覆盖 → rotate 后消失）。
3. **任务文件名 `kubeconfigs.yml`**：仓库 `.gitignore` 有 `kubeconfig.*` 规则，会把
   `tasks/kubeconfig.yml` 吞掉（发现于 A1 断言）。故改名，并保留 A1 的 git 忽略检查防回归。
4. **沙箱 apiserver 只开 RBAC**：Node authorizer 会给 `system:node:*` 隐式放行
   secrets/pods 等（与「kubelet 最小权限」断言冲突，且不可观测）。测试内
   `kube_apiserver_authorization_mode: "RBAC"`，使 `can-i` 结果**只反映本 role 的 RBAC 清单**；
   生产默认仍为 `RBAC,Node`（role defaults 未改）。
5. **`ready` 插件端口变量化**：`ready` 默认监听 `:8181`，不在 metrics 端口上（首轮曾误判 404）。
   新增 `cluster_addons_coredns_ready_port`（空 → 插件默认；非空 → `ready :PORT`）。
6. **CoreDNS 制品走 download role**：tarball 落沙箱 artifacts（sha256 校验），
   解包到沙箱 `usr/local/bin`；不写宿主 `/usr/local/bin`。
7. **测试端口**：API 16443、etcd 12379、DNS 15353、metrics 19153、ready 19156、
   upstream 15354、bad-instance DNS 15355；不与默认端口冲突。
8. **`dnsq.py` 手写 DNS**：环境无 `dig`/dnspython；仅解析 A 记录 + RCODE，超时退出码 2。

## 5. 受限声明（对应 spec R1 v1.4 / C13）

### 5.1 CoreDNS Pod 未运行（受限）

无镜像/registry 不可达，CoreDNS **Deployment 未被 apply、Pod 未 Running**。
`kubectl -n kube-system get pods`、Pod 就绪、Service 端点均未验证。
本任务只保证清单可渲染、可解析、变量一致。

### 5.2 集群内 DNS 未验证（受限）

D1/D2 的解析来自 **CoreDNS 官方二进制进程**（宿主 netns 内高位端口），不是
`kube-dns` Service 的 ClusterIP:53，也不是 Pod 网络。因此「Pod 内 `/etc/resolv.conf`
指向 10.96.0.10 且能解析」**未验证**。真机步骤见 §5.6。

### 5.3 kubelet 运行态未验证（受限）

`kubelet.conf` 的身份与 RBAC 边界已验证，但 kubelet 进程未在本任务启动
（T012/T014）。因此「kubelet 用该 kubeconfig 注册 Node 成功」未验证。

### 5.4 Node authorizer 未覆盖（受限）

沙箱 apiserver 以 `RBAC` 单模式运行（§3.3-4）。生产 `RBAC,Node` 下 kubelet 的
实际权限是 **RBAC ∪ Node authorizer**，会更大（如可读 secrets）。本任务验证的是
「role 渲染的 RBAC 清单边界」，不声称 kubelet 在 Node authorizer 下无 secrets 权限。

### 5.5 未实现的高级能力（非目标）

NodeLocal DNSCache、`kube-dns` ConfigMap 自动同步、CoreDNS HPA/PDB、指标采集、
证书自动轮换（kubelet CSR）均不在本任务。

### 5.6 真机复验步骤（必做，目标真机执行）

kubectl --kubeconfig /etc/kubernetes/admin.conf apply -f /etc/kubernetes/addons/manifests/coredns.yaml

# 2) 运行态（本任务未验证，真机必须做）

  --image=<可达镜像> -- sh -c 'nslookup kubernetes.default.svc.cluster.local'
